# حماية ملكية طلب الدفع — 2026-10-14

## النتيجة

TXID وOrder ID يحددان تحويلًا، ولا يثبتان أن حساب Telegram الذي أرسلهما يملك التحويل. النظام الآلي يعتمد فاتورة أنشأها الخادم لصاحب طلب محفوظ، ويثبت وصول الدفع من API المزود قبل تسجيله مرة واحدة. هذا يثبت الجهة المستفيدة من طلب الدفع؛ لا يثبت الهوية القانونية لمن دفع، وقد يدفع شخص فاتورة شخص آخر.

استخدمت مراجعة Python القائمة على مبادئ OWASP والتوثيق الرسمي للمزود. مسارات الدفع هنا Python ووحدات stdlib، وليست Flask أو Django أو FastAPI؛ لم تُطبق إرشادات إطار غير موجود.

## 1. خطورة حرجة: اعتماد تحويل عام لصاحب رسالة Telegram

**الأثر:** كان يمكن لمن ينسخ مرجع تحويل أن يضيف قيمته لمحفظته أو يموّل ملفه، دون إثبات أن التحويل يخص طلبه.

السبب في الواجهة القديمة: `BinancePayClient.verify_payment` كان يقبل كذلك رقم الدافع، و`_handle_user_text_input` كان يعتمد الوصول نفسه كملكية ثم يستدعي شحن المحفظة. لم يكن أول استخدام للمرجع، ولا مطابقته للمبلغ، إثباتًا للمالك.

الإصلاح في المصدر:

- [crypto_pay.py](E:/Projects/smart_zainchecker_gemini/telegram_bot/crypto_pay.py:242): دالة الواجهة القديمة لا تعطي تصريحًا ماليًا لمرجع تحويل؛ رقم الدافع ليس معرف عملية.
- [bot.py](E:/Projects/smart_zainchecker_gemini/telegram_bot/bot.py:796): إرسال TXID إلى مساري الشحن والملف القديمين لا يشغّل التحقق المالي أو الشحن أو الفحص. الطلبات القديمة باقية للمراجعة.
- [payments.py](E:/Projects/smart_zainchecker_gemini/telegram_bot/commerce/payments.py:34): تحميل الطلب يتحقق من صاحبه، ثم يطابق التطبيق والفاتورة والمبلغ والأصل والتوقيت وpayload.
- [invoice_monitor.py](E:/Projects/smart_zainchecker_gemini/telegram_bot/commerce/invoice_monitor.py:31): المراقبة تختار الفواتير المرتبطة في قاعدة البيانات؛ لا تأخذ TXID أو صاحب دفع من رسالة العميل. التحقق مجمع ومحدود بعشرين طلبًا في الدورة، ويستخدم قيد قاعدة البيانات لمنع التكرار.

المسار الآلي للفواتير المضافة هو Crypto Pay. أضيف لاحقًا مسار لحساب Binance العادي يعتمد رمزًا خاصًا في ملاحظة التحويل قبل الدفع؛ الاعتماد العام محجوب حتى ينجح اختبار وصول الملاحظة الحقيقي. التحويل الذي لا يحمل رمز طلب سابق، وBSC، يبقيان للمراجعة. لا توجد آلية مفعلة لتوقيع محفظة BSC أو OAuth يربط حساب Binance بالمستخدم.

## 2. خطورة مرتفعة: إخفاء سجل الطلبات عن العميل عند الضغط الفعلي

كان معالج سجل الطلبات يراجع الملكية، لكن بوابة callback العامة لا تسمح بزر `oh:` للعميل. أُضيف مروره في [ui.py](E:/Projects/smart_zainchecker_gemini/telegram_bot/ui.py:248)، مع بقاء فحص المالك وصلاحيات الإدارة داخل المعالج. اختبارات الأزرار الفعلية تثبت أن العميل يفتح طلبه، وأن أمر إدارة مزور لا يعرض طلبات الآخرين.

تضيف migration 025 سجل الطلبات والمحفظة من الخادم، دون الاعتماد على بقاء مسودة محلية. الوصول للطلب والصندوق المالي يحدد من هوية Telegram المتحققة؛ أدوار anon وauthenticated لا تصل إلى RPC الخلفية أو جداولها.

## 3. التحويل القديم المختلف عليه

قراءة واحدة من API Binance أعادت خمس معاملات. المرجعان في تاريخ الحسابين 442426326 و545342618 طابقا معرف المعاملة الحقيقي نفسه. حُفظت بصمات المعرفات في دليل خاص خارج Git، ولم تتغير الأرصدة أو السجلات.

هذه القراءة تثبت تطابق المعاملة، ولا تحدد أي حساب Telegram يجب أن يستفيد منها. لا يوجد ربط سابق مثبت بين التحويل وأحد الحسابين. يبقى نقل هذا الرصيد محجوبًا حتى توفر دليل ملكية مستقل أو قرار تسوية موثق من الإدارة؛ لا يُختار أول من يرسل المرجع.

## كيف تعمل الآلية المفضلة

1. يطلب العميل الشحن في محادثته الخاصة.
2. يحفظ الخادم هوية العميل والسعر والعملة والمدة ومعرف طلب عشوائي.
3. ينشئ المزود فاتورة مرتبطة بهذا الطلب. لا يختار العميل invoice_id بديلًا.
4. تُراجع الفاتورة بواسطة API المزود، مع تطابق الحساب المستلم والمبلغ والعملة والمدة وبيانات الربط.
5. يسجل الخادم الدفع لصاحب الطلب المحفوظ داخل معاملة واحدة. تكرار الرسالة أو الفحص أو انقطاع الرد لا يضيف دفعة ثانية.

لـ Binance Pay Merchant يمكن استخدام merchantTradeNo وpassThroughInfo، مع الاستعلام الموثق لدى المزود والتحقق من توقيع webhook إن استُخدم. مفاتيح قراءة SAPI الموجودة لا تكفي لإثبات أن خدمة Merchant مهيأة. هذا الربط غير منفذ أو مفعّل في النسخة الحالية.

إثبات التحكم بمحفظة ذاتية الحفظ يمكن أن يستخدم توقيع رسالة بمعرف تحدٍ ومدة ونطاق حسب ERC-4361، ثم يطابق عنوانها بمصدر التحويل. هذه آلية أخرى لم تُضف، ولا تصلح افتراضًا لسحب من محفظة منصة مشتركة. صورة الإيصال أو الاسم أو تطابق المبلغ وحدها ليست بديلًا للتحقق من الحساب أو توقيع المحفظة.

- [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361): التحقق من توقيع المحفظة والنطاق ومعرف التحدي والمدة.

## تحديث: حساب Binance العادي دون Merchant

أظهرت قراءة API الفعلية حقل note ومعرف الدافع في سجلات الحساب. الملاحظات المتاحة كانت فارغة، لذلك لم يثبت انعكاس نص ملاحظة فعلية حتى الآن. يدعم [دليل إرسال Binance Pay](https://www.binance.com/en-NG/support/faq/detail/b3fa3ae045b9429084203c3a4ff1362f) كتابة ملاحظة قبل تأكيد التحويل. ربط الحساب عبر [Binance OAuth](https://developers.binance.com/en/docs/products/login/app-integration) يتطلب تسجيل تطبيق متاح حاليًا لشركاء المنظومة؛ ليس إعدادًا مفترضًا لحساب عادي.

migration 027 تحفظ رمزًا عشوائيًا فريدًا مرتبطًا بطلب واحد وصاحبه وUID المرسل قبل الدفع. الرمز لا يعاد إسناده أو تغييره. Backend يراجع الملاحظة من سجل المزود الموثق، والمستلم ونوع C2C والحساب المرسل والمبلغ والعملة والمدة ومعرف العملية الحقيقي، ثم يسجل قيدًا واحدًا لصاحب الطلب المحفوظ. الرقم المُدخل في Telegram لا يصبح دليل ملكية ولا يغير المستفيد.

الدليل المحلي `acceptance_binance_note_fbc4eaab7284.json`: 32 محاولة متنافسة، منها 16 لطلب آخر، انتهت بدفعة واحدة و3000 قرش لصاحب الرمز، وصفر للحساب الآخر. سجل RPC ممنوع على العميل. هناك أيضًا اختبارات الرمز الغائب والمعدل والمرسل والمستلم الخاطئ والعملية القديمة والتكرار وغموض عدة دفعات بالرمز نفسه. ادعاء الوصول بملاحظة في نص المحادثة وحده لا يعتمد.

قراءة الهوية الحالية استنتجت توافق uid في سجل الحساب مع UID مستلم التحويلين الواردين؛ هذا لا يثبت وحده تطابق Pay ID المضبوط معه. بعد اختبار الملاحظة يجب تثبيت UID المستلم الفعلي في إعداد route ومطابقته، ولا نعتمد غياب accountId بدلًا من التطابق. إعداد route الحالي يحفظ Pay ID فقط، ولذلك يبقى مسار الملاحظة العام معطّلًا.

أداة `binance_note_probe` جهزت رمز اختبار منفصلًا يبدأ بـ ZTEST، لا يقبله مسار الأموال الذي يبدأ رمزه بـ ZC. الاختبار يقرأ وصول الملاحظة فقط، ولا يضيف رصيدًا أو يفتح بوابة الدفع أو يحدد صاحب التحويل القديم. التحويل الفعلي يرسله المستخدم بنفسه في Binance؛ لم ينفذ البرنامج أي تحويل صادر.

Supabase الآن إصدار 27 مع 35 جدولًا خاصًا و74 دالة للخلفية، مع RLS ومنع anon/authenticated وتطابق بصمات migrations. تحقق التشغيل: `runtime_verification_20261014T171557Z.json`. الأرصدة القديمة لم تنقل، وقوائم الطلبات والمدفوعات والقيود المالية الجديدة فارغة. التطبيق المحلي الجاري لم يُعد تشغيله، واستقبال البوت بقي معطّلًا مؤقتًا.
