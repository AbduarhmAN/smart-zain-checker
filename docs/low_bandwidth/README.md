# محرك استعلام الخدمة عبر HTTP — التحقق على VPS

يضيف هذا التعديل محركاً اختيارياً لاستعلام أرقام الخدمة، مع الاحتفاظ بمسار أرقام الحسابات والنتائج والفوترة والطابور القائم. لا يشغّل البرنامج أو يرفع وضع الصيانة تلقائياً.

## ما تم اختباره

- نجحت النسخة الأصلية على VPS في 3/3 استعلامات بعد استخدام `socks5h` لحل اسم الوجهة عبر البروكسي نفسه. تعثرت محاولتا `socks5` الأوليان قبل استلام صفحة الموقع، بسبب تعذر وصول SOCKS إلى المضيف.
- نجح المحرك المدمج في 3/3 استعلامات مماثلة، ثم في استعلامين عبر بروكسيَي الخدمة الموجودين، ثم في استعلامين عبر `WorkerActor` الفعلي. تطابقت المبالغ مع العينة السابقة الموثقة.
- نجح 108 اختبارات محلية، و24 اختباراً على Linux في نسخة معزولة من كود VPS الحالي. لا تتضمن هذه الاختبارات شحناً أو خصماً أو تسوية مالية حقيقية.
- بلغ مجموع أحجام حزم IPv4 المرصودة باتجاهي الاتصال في العينة المقارنة 131,077 بايت للنسخة الأصلية و70,527 بايت للنسخة المدمجة: انخفاض مرصود 46.19%. القياس من `tcpdump` مع مطابقة منافذ المقابس التابعة لعملية الاختبار، ويشمل حمل TCP/IP وTLS والنفق؛ ليس قياساً لفاتورة مزود البروكسي.
- لا تمثل إعادة ضغط HTML قياساً لحركة الشبكة، ولذلك لا يعلن المحرك قيمة `wire_kb` تقديرية. يعرض بايتات النص المفكوك وعدادات libcurl المتاحة. قد يكون عداد التنزيل غير متاح بعد القطع المبكر، وعندها تكون قيمته `null`.

هذه عينة توافق محدودة وليست اختبار حمل لمدة ساعة أو تحققاً من 325 بروكسياً. لم يثبت هذا الاختبار معدل 23,500 استعلام/ساعة أو ضمان عدم الحظر. عند 325 مساراً وزمن استجابة 4 ثوانٍ وتبريد 60 ثانية بعد الاكتمال، السقف الحسابي 18,281 استعلاماً/ساعة تقريباً قبل بقية القيود. حد الإرسال الافتراضي في هذا الإصدار 5 استعلامات/ثانية، وعدد المسارات المنشورة يبقى كما هو؛ لم تُوسّع قائمة البروكسيات.

الدليل المجمع القابل للنشر: [validation_20261021.json](validation_20261021.json). لا يتضمن بيانات العملاء أو بيانات دخول البروكسي.

## الدقة والحماية التشغيلية

- تُقبل النتيجة المالية فقط من JSON صالح في `quickpayData`، بمبلغ محدود وصالح ورقم حساب صالح، واستجابة HTTP 200 من الوجهة المطلوبة.
- لا تتحول صفحة دخول أو خط مسبق الدفع أو نص صفر في قالب الصفحة إلى رصيد صفر متحقق منه. تذهب النتائج غير المتحققة إلى مسار المراجعة القائم.
- يُفك UTF-8 تدريجياً، ويُقرأ JSON بأرقام Decimal، ويُوقف الاستقبال فور اكتمال النتيجة، مع إغلاق الجلسة دائماً وحد أقصى 128 KiB للمحتوى المفكوك.
- مجدول واحد داخل عملية المحرك يفرض تبريد المسار 60 ثانية بعد انتهاء المحاولة، ويحترم `Retry-After` ويحد التوازي بـ28. مفاتيح المسارات بصمات لإعداد الاتصال وليست إثباتاً لعنوان الخروج العام.
- لا يُغيّر المحرك البروكسي عند الفشل، ولا ينتقل تلقائياً إلى الاتصال المباشر أو المتصفح. يوقف التحقق أو الحظر المسار حتى مراجعة المشغل؛ زر استئناف المسار يزيل عزله بعد المراجعة ويظل التبريد سارياً.

## التثبيت والتفعيل

ثبّت `requirements-low-bandwidth.txt` في بيئة Python منفصلة مع تبعيات البرنامج المعتادة. الإصدار الاختباري المثبت هو `curl_cffi==0.15.0`، والمستند التقني للمكتبة متاح في [توثيق curl_cffi](https://curl-cffi.readthedocs.io/en/v0.15.0/api.html).

الإعداد الافتراضي يبقي المتصفح. لتفعيل المحرك على مسارات مختبرة فقط:

```text
ZAIN_SERVICE_ENGINE=low_bandwidth
ZAIN_SERVICE_HTTP_ROUTES=<comma-separated route_key values>
```

تُستخرج البصمات من `engine_v3.proxy_scheduler.route_key` باستخدام إعدادات البروكسي الخاصة على الخادم، ولا تُنشر بيانات الدخول في المستودع. الاتصال المباشر يظل على مسار المتصفح ما لم يُفعّل `ZAIN_SERVICE_HTTP_ALLOW_DIRECT=1` صراحةً بعد اختباره. لا تُضمَّن ملفات التشغيل أو ملفات العملاء في GitHub.

في VPS جرى اختيار بروكسيَي الخدمة الحاليين المختبرين. ما زال أرقام الحسابات على مسارها القائم، وما زالت خدمة البوت الطبيعية متوقفة ومجيب الصيانة يعمل.

## الرجوع

أعد `ZAIN_SERVICE_ENGINE=browser` واستخدم مفسر Python السابق أو عطّل ملف override الخاص بالمحرك قبل إعادة تحميل systemd. احتفظ بالنسخة الاحتياطية للمصدر ووحدة الخدمة؛ لا تُعدّل دفاتر المحفظة أو الطابور أو مؤشرات تسليم Telegram. لا يتطلب التراجع إعادة إرسال ملفات العملاء.
